# 下一次 GPU 训练之前的工作顺序

2026-10-06，补充本轮结案。λ=1 是下一次**训练实验**的首选，不是全部项目工作的唯一首选。先做有边界的本地保真核验和性能诊断，再决定是否满足新训练的条件。

## 1. Act2 保真度核验：优先于新 GPU 提交

已有 Snecko 字节码及native修复、Book/Byrd/Slavers等有限受控场景，仍缺真实游戏的完整交互链证据。采用正常开发开局失败的实际上下文，优先核验：

- Book of Stabbing：父模型73次、终点42次Act2死亡上下文。
- Shelled Parasite + Fungi Beast：59/43次。
- Byrds：70/27次。
- Slavers：49/41次；Snake Plant：47/38次。

这些是最后失败上下文计数，不是遭遇率或难度排序，也没有证明这些遭遇存在bug。先覆盖3个代表性高频交互，再根据差异扩大；不以无限期完成全内容parity为前置要求。核验公共状态、合法动作、伤害/状态/死亡回调、奖励与相关RNG推进；不能只比较最终HP或让native实现给自己生成预期。

奖励预览须核验UI可达性与领取顺序。当前original adapter明确把父奖励页和子卡牌页合并为一次决策；Oracle提供预览字段。原版可免费查看的信息与不可见信息应区分，不沿用旧报告直接把全部卡牌预览判为作弊。Smoke Bomb和盗贼逃跑也已存在分支处理，不能据`addPotionRewards`旧注释直接判定尚未修复。

如果发现影响规则、observation/action或RNG的真问题：单独修复、版本化、迁移并重评冻结模型。**若新λ训练采用修复后的契约，本轮旧λ=.98训练不再是严格单变量训练对照**；需要同新契约重建control，或明确只做新配方效果验证，不能将规则修复收益归到λ。

## 2. 吞吐：先测量，再做一个语义保持优化

本轮update约99.66 decisions/s；encode占28.35%，transition占23.72%，optimizer占26.61%。这些计时层级不能任意相加，也不是GPU利用率。优先细分编码、padding/张量构造、对象转换、IPC和等待。

使用warm-up、固定线程和同步正确的计时；[PyTorch benchmark官方说明](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)强调线程和CUDA同步影响比较。

首个目标是找到可减少重复编码/分配/复制的热点，再固定输入核对entity/action IDs、mask、全部输入tensor、logprob/value，以及固定rollout更新结果。只缓存真正静态的内容；不缓存变化的费用、合法动作、遗物计数或更新后的神经特征。

理想化地把28.35%的encode耗时减半，总加速只有约1.165倍；这不是已测得收益。实际按端到端墙钟验收，包含评估成本。暂不混入mixed precision、worker数量和rollout长度变化，避免同时改变学习行为。Windows改善不等于NUS改善，服务器需短benchmark确认。

## 3. 学习机制和策略诊断

保持λ单变量实验为第一训练选择，但先补充不依赖大规模训练的诊断：共享critic/actor梯度干扰、失败/成功轨迹的优势信号、recurrent片段旧memory与当前参数偏差，以及正常入幕的构筑/路线/药水行为。当前证据不能认定它们全部有bug。

策略改善围绕正常开局联合成功：Act1如何为Act2构筑、Act2普通战/精英多目标及药水使用。约91%的Act2失败在Boss前，不能用只练Boss代替这部分。Neow已有内容表征，位置集中和几乎不swap只是覆盖信号，不足以证明应该鼓励swap。扩大网络、蒸馏保住Act1行为或加入Act1生存奖励均不优先。

若λ有限试验仍没有联合收益，下一重点转为自然Act2入幕状态的suffix课程及critic适应：保留真实牌组/relic/资源/RNG/前缀和循环状态，禁止凭空制造理想牌组。辅助训练改变start distribution，必须独立立契约，最终仍按正常Neow开局联合胜率验收。

## 执行边界

先完成上述有限核验、profiling和必要修复，记录结果，再冻结下一次训练的contract。没有阻断性差异时执行原λ设计；存在契约变化时先修订对照设计。日常局部机制探针和短benchmark可在本地完成；本轮未启动新NUS训练、未执行新的真实游戏轨迹，也未宣称获得吞吐提升。
